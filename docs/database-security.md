# Supabase 접근 보안 적용

대상 프로젝트: `break-timer` (`pqqelfnsulqfdjrwlbly`).
지정 관리자: 앱 아이디 `admin`에 대응하는 `admin@test.com`의 확인된 Supabase Auth 계정.
이는 Supabase 대시보드에 로그인하는 계정과 별개다.
앱의 아이디→이메일 변환은 `store/useAuthStore.ts`에서 확인할 수 있다.

## 운영 적용

1. Supabase 대시보드의 Authentication → Users에서 관리자 계정과 이메일 확인
   상태를 확인한다. 계정이 없으면 먼저 해당 관리자의 Auth 계정을 준비한다.
   다른 로그인 계정을 자동으로 관리자에 포함하지 않는다.
2. 해당 프로젝트의 SQL Editor에서
   `supabase/migrations/20261007000001_secure_admin_access.sql` 전체를 실행한다.
   관리자 계정이 없거나 확인되지 않았으면 트랜잭션이 실패하고 변경되지 않는다.
3. `supabase/migrations/20261007042246_remove_legacy_access_policies.sql`을 실행해
   Advisor가 지적한 예전의 전체 로그인 사용자 허용 정책을 제거한다.
4. `supabase/verify-admin-access.sql` 전체를 실행한다. 성공 메시지를 확인한다.
5. 앱에서 관리자 로그인 후 직원 조회·등록·수정, 근무표 저장, 휴게 설정 저장을
   확인한다. 테스트로 만든 항목은 확인 후 정리한다.
6. Security Advisor를 새로 실행한다. 다른 테이블의 경고가 남으면 해당 테이블의
   용도와 권한을 별도로 확인한다. 이 변경의 대상은 세 앱 테이블이다.

## 정책

- `employees`, `work_schedules`, `daily_break_settings`에 RLS를 활성화한다.
- `anon`과 `PUBLIC`의 테이블 권한을 회수한다.
- `authenticated`에는 조회·삽입·수정·삭제 권한만 주고, RLS로 등록 관리자만 허용한다.
  기존의 느슨한 허용 정책이 있어도 제한 정책이 비관리자 접근을 차단한다.
- 관리자 UUID는 API에 노출하지 않는 `break_timer_private.admin_users`에 저장한다.
  브라우저 클라이언트는 이 목록을 조회하거나 수정할 수 없다.
- `service_role`과 DB 소유자는 관리용 접근을 유지한다. 이 자격 증명은 브라우저에
  제공하면 안 된다. 공개 anon 키는 비밀 키가 아니며, 접근 제어는 DB 정책이 담당한다.
- `break_timer_private`를 Supabase Data API의 노출 스키마에 추가하지 않는다.

운영 DB가 직접 변경되기 전에는 저장소의 SQL 수정만으로 노출이 해소되지 않는다.
과거 유출 여부는 이 변경으로 판단할 수 없다. 기존 API·Auth 로그를 별도로 확인한다.

## 유출 비밀번호 검사 경고

`auth_leaked_password_protection`은 RLS와 별개인 Auth 설정이다.
Supabase 대시보드의 Authentication 설정에서 Leaked Password Protection을 켠다.
사용 중인 요금제에서 제공되는지 확인하고, 설정이 없으면 이 기능의 이용 조건을 확인한다.
이 기능을 켜는 것만으로 기존 비밀번호가 변경되지는 않는다. 관리자 비밀번호는
길고 고유한 값으로 별도로 변경한다.

## 운영 확인 기록 (2026-10-07)

Supabase 플러그인으로 운영 DB를 확인하고 기존 전체 사용자 허용 정책 두 개를
제거했다. 세 앱 테이블의 RLS가 활성화되어 있고 익명 테이블 접근 권한은 없다.
허용 목록에는 `admin@test.com` 계정 하나만 있다. 운영 검증 SQL도 통과했다.

남은 Advisor 항목은 다음과 같다.

- `rls_enabled_no_policy` (INFO): 비공개 관리자 목록의 RLS에 클라이언트 허용 정책이
  없는 상태다. 목록은 클라이언트 접근을 막고 내부 관리자 판별 함수에서만 읽으므로
  허용 정책을 추가하지 않는다.
- `auth_leaked_password_protection` (WARN): 현재 Free 요금제에서는 제공되지 않는다.
  공식 문서 기준 Pro 이상에서 이용 가능하다. 자동으로 요금제를 변경하지 않는다.

## 마이그레이션 이력 정렬 (2026-10-07)

운영 스키마와 관리자 접근을 검증한 뒤, 수동 적용되어 이력이 빠졌던
`20260913000000`, `20260914000001`, `20261007000001`을 운영 이력에 등록했다.
DB 변경 SQL을 다시 실행하지 않고 이력 테이블에 버전·이름·SQL 내용만 보충했다.
이 기록은 실제 적용 시각을 증명하는 감사 로그가 아니라 적용 상태를 보정한 것이다.

정책 정리 파일은 플러그인이 기록한 운영 버전 `20261007042246`에 맞춰 이름을
변경했다. 로컬 파일과 운영 이력의 네 버전 및 SQL 내용이 일치한다.

앞으로 플러그인으로 적용한 뒤에는 반환된 운영 버전을 조회해 로컬 파일 이름과
맞춘다. 적용된 파일을 수정하기보다는 새 마이그레이션으로 후속 변경을 기록한다.

이 폴더는 기존 DB의 후속 변경 이력이다. 최초 앱 테이블 생성은 `docs/schema.sql`에
남아 있으므로, 빈 DB에 이 폴더만 실행하는 것으로 전체 초기화가 완료되지는 않는다.
새 환경에는 기본 테이블과 확인된 관리자 Auth 계정을 먼저 준비해야 한다.
